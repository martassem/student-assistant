# Аналіз технічного завдання проєкту Student Assistant

## Функціональні вимоги

Проєкт Student Assistant — це навчальний кросплатформний застосунок-планувальник завдань студента.

Основні функції, які повинні підтримувати клієнти:

* перегляд списку навчальних завдань;
* додавання нового завдання;
* зазначення назви завдання;
* встановлення дедлайну;
* встановлення пріоритету завдання;
* позначення завдання як виконаного або невиконаного;
* редагування існуючого завдання;
* видалення завдання;
* фільтрація або сортування завдань за станом виконання;
* фільтрація або сортування завдань за пріоритетом.

Фільтрація та сортування визначені як бажана функція, тому вона не обов'язково повинна бути реалізована в кожному окремому клієнті.

Усі клієнтські модулі повинні працювати зі спільним набором навчальних завдань та використовувати однаковий формат даних.

## Нефункціональні вимоги

* Система повинна бути кросплатформною.
* Сукупність клієнтських модулів повинна забезпечувати підтримку Windows, macOS та Linux.
* Клієнти повинні бути незалежними та незалежно розгортатися.
* Клієнтські модулі не повинні мати прямих залежностей один від одного.
* Обмін даними між модулями здійснюється через спільний файл `data/tasks.json`.
* Кожен клієнт повинен використовувати узгоджену структуру даних.
* Зміни у форматі спільних даних повинні бути узгоджені та зафіксовані в документації проєкту.
* Розробка та історія змін повинні вестися за допомогою Git і GitHub.
* Для окремих задач передбачається використання окремих гілок та Pull Request.
* Проєкт повинен містити документацію у файлі `README.md`.
* Аналіз технічного завдання зберігається у файлі `docs/tz-notes.md`.

## Модулі та технології

Проєкт складається з чотирьох незалежних клієнтських модулів.

| Модуль                     | Технологія         | Призначення                                     |
| -------------------------- | ------------------ | ----------------------------------------------- |
| Веб-клієнт                 | React + CSS        | Веб-інтерфейс для роботи із завданнями          |
| Десктопний контейнер       | Electron або NW.js | Десктопна оболонка для веб-інтерфейсу           |
| Нативний десктопний клієнт | C++ / Qt           | Нативний кросплатформний клієнт                 |
| Аналітичний модуль         | Python / Flet      | Аналіз та представлення інформації про завдання |

Усі модулі працюють зі спільним файлом `data/tasks.json`.

Між клієнтами не повинно бути прямих залежностей. Кожен модуль розробляється та розгортається окремо.

Розробка відбувається поетапно відповідно до тем курсу:

1. Підготовка репозиторію, Git, GitHub та робочого середовища.
2. Розробка веб-клієнта на React.
3. Розробка десктопного контейнера на Electron або NW.js.
4. Розробка нативного клієнта на C++/Qt та аналітичного модуля на Python/Flet.
5. Інтеграційне тестування всієї системи.

## Формат обміну даними

Основним спільним джерелом даних є файл:

`data/tasks.json`

Файл містить масив JSON-об'єктів. Кожне завдання має такі поля:

| Поле        | Тип     | Призначення                           |
| ----------- | ------- | ------------------------------------- |
| `id`        | число   | Унікальний ідентифікатор завдання     |
| `title`     | рядок   | Назва завдання                        |
| `completed` | boolean | Стан виконання завдання               |
| `dueDate`   | рядок   | Дедлайн у форматі `РРРР-ММ-ДД`        |
| `priority`  | рядок   | Пріоритет: `low`, `medium` або `high` |

Приклад одного запису:

```json
{
  "id": 1,
  "title": "Підготувати конспект лекції 2",
  "completed": false,
  "dueDate": "2026-09-15",
  "priority": "high"
}
```

Поле `id` повинно бути унікальним.

Поле `completed` може мати лише значення `true` або `false`.

Поле `priority` повинно містити одне з трьох значень:

* `low` — низький пріоритет;
* `medium` — середній пріоритет;
* `high` — високий пріоритет.

Усі клієнти повинні дотримуватися єдиного формату даних і не змінювати структуру `tasks.json` без узгодження.

## Відкриті питання

Під час аналізу ТЗ виникли питання, які бажано уточнити перед подальшою розробкою:

1. Чи повинні всі чотири клієнти обов'язково реалізовувати абсолютно однаковий набір функцій, чи окремі функції можуть відрізнятися залежно від призначення клієнта?
2. Чи є фільтрація та сортування обов'язковими для веб-клієнта, чи вони залишаються лише бажаною функцією?
3. Яким чином повинні оброблятися ситуації з однаковими `id` під час додавання нових завдань?
4. Чи потрібно перевіряти коректність формату дати `dueDate` перед записом у `tasks.json`?
5. Чи повинні клієнти повідомляти користувача про помилки читання або запису `tasks.json`?
6. Чи потрібно реалізувати одночасне використання кількох клієнтів та передбачити ситуацію, коли два клієнти змінюють файл даних одночасно?
7. Які саме функції аналітики повинні бути реалізовані в модулі Python/Flet?
8. Які конкретні вимоги до дизайну та адаптивності веб-інтерфейсу потрібно виконати?
9. Чи буде для оцінювання достатньо локальної роботи з `tasks.json`, чи передбачатиметься додаткове тестування на різних операційних системах?
10. Які критерії будуть використовуватися для перевірки інтегрованої роботи всіх чотирьох клієнтів?
